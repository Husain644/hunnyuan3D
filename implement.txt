Transform the existing Image → 3D project into a genuinely reproducible, one-command setup for a completely new developer/server.

## GOAL

After a developer clones the GitHub repository onto a compatible GPU machine, they should be able to run ONE setup/start command and get a fully working application.

Target workflow:

```bash
git clone <repository>
cd <project>
./setup.sh
```

After setup completes:

* dependencies installed
* Python environment created/configured
* FastAPI application configured
* required directories created
* required model/checkpoint files downloaded or verified
* environment/configuration prepared
* application started
* public Image → 3D page accessible
* 2.1 single-view generation works
* 2mv multi-view generation works
* GLB result/download works

A new developer should NOT need to manually execute a long list of commands.

IMPORTANT:

First inspect the complete repository and understand the current working deployment.

The current project already has:

* FastAPI public Image → 3D application
* Hunyuan3D-2.1 pipeline
* Hunyuan3D-2mv adapter
* public generation API
* model selector
* single-view generation
* multi-view generation
* GLB result/download
* object name
* object description
* front/back/left/right views
* job/status/result flow

Preserve all currently working functionality.

Do NOT migrate the project to Django or introduce Django.

Use the existing FastAPI architecture.

==================================================

1. ONE COMMAND
   ==================================================

Create one canonical bootstrap command:

```bash
./setup.sh
```

It must be safe to run from a fresh clone.

If setup has already been completed, running it again should be idempotent:

* don't unnecessarily redownload huge model files
* don't recreate working environments
* don't destroy existing generated data
* verify existing dependencies instead
* repair missing pieces when possible

If technically cleaner, setup.sh may prepare everything and then start the application.

If setup and startup need to remain separate, provide:

```bash
./setup.sh
./run.sh
```

But minimize the number of commands required for a new developer.

==================================================
2. HARDWARE DETECTION
=====================

Detect the machine before installing GPU dependencies.

Check:

* NVIDIA GPU availability
* GPU name
* VRAM
* NVIDIA driver
* CUDA compatibility
* Python version

Print a clear summary:

```text
========================================
Image → 3D Setup
========================================

GPU: NVIDIA RTX 4090
VRAM: 24 GB
CUDA: ...
Python: ...
========================================
```

Do not hard-code RTX 4090/T4/etc.

The project should work on compatible NVIDIA GPUs within the actual memory requirements of the installed models.

If no compatible GPU is detected, stop with a useful explanation instead of failing later during model loading.

Do NOT automatically install NVIDIA drivers.

Do NOT perform dangerous system-level GPU modifications.

==================================================
3. PYTHON ENVIRONMENT
=====================

Create a project-local virtual environment:

```text
.venv/
```

Do not require the developer to manually activate it.

The setup script should directly use:

```text
.venv/bin/python
.venv/bin/pip
```

Detect and validate the Python version based on the actual FastAPI/Hunyuan requirements.

Create a clean dependency strategy.

For example:

```text
requirements.txt
requirements-gpu.txt
```

or another structure if the current repository already has a better one.

Pin important versions where required for reproducibility, especially:

* torch
* torchvision
* CUDA-specific PyTorch packages
* Hunyuan dependencies
* FastAPI
* Uvicorn
* related inference libraries

Do not randomly upgrade working packages.

==================================================
4. MODEL/CHECKPOINT MANAGEMENT
==============================

This is critical.

Do NOT make a new developer manually download checkpoints.

Create a model bootstrap system.

For example:

```text
models/
  hunyuan3d-2.1/
  hunyuan3d-2mv/
```

Use the actual model structure required by the current implementation.

The setup process must:

1. Check whether required checkpoints exist.
2. Verify that they are complete.
3. Download missing checkpoints automatically.
4. Never redownload an existing valid checkpoint.
5. Show useful download progress.
6. Fail with a clear error if authentication/access is required.

Do NOT commit multi-GB model weights into Git.

Use environment/configuration variables for model locations where appropriate.

Document:

* exact model name
* source
* expected files
* approximate size
* whether Hugging Face authentication is required
* license/usage requirements

The application should detect missing model files at startup and give a useful message.

5. CONFIGURATION
================

Create a clean environment configuration system.

Provide:

```text

```

with all required variables.

Inspect the existing code and use the actual variable names where possible.


Do not invent variables that the application does not need.

setup.sh should create `.env` from `.env.example` if it does not exist.

Never commit:

* local machine paths

Do not hard-code paths such as:

```text

/home/user/...
/workspace/...
/mnt/...
```

Everything must use project-relative paths or environment variables.

==================================================
8. MODEL LOADING
================

Inspect how the current application loads Hunyuan3D.

Do not unnecessarily load both large models into VRAM simultaneously if the current GPU cannot safely hold them.

Preserve the existing model-loading strategy.

If the application already has lazy loading/model caching, keep it.

The final setup must not accidentally cause:

```text
2.1 + 2mv
```

to simultaneously consume all GPU memory unless the existing hardware supports it.

If model switching requires unloading one model before loading another, implement that safely.

==================================================
9. PUBLIC API
=============

Preserve the existing public API:

```text
POST /v1/public/generate/upload
```

It currently supports:

```text
model=2.1|2mv
view_front
view_back
view_left
view_right
name
description
```

Do not break this API.

Expected behavior:

### 2.1

Main image is used for the existing 2.1 workflow.

### 2mv

Front view is required.

Back/left/right are optional.

Use the actual 2mv adapter.

Invalid model:

```text
HTTP 400
```

2mv without the required front view:

```text
HTTP 400
```

Keep the existing response structure unless there is a strong reason to change it.
